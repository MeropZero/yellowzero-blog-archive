## 1. 方案总览：「Git 管内容 + 国内托管管访问」

核心思想：**不赌单边**，把"内容保险"和"访问体验"两个目标分别交给各自最合适的平台，二者通过 git 统一管理、相互兜底。

```
┌──────────────────────────────────────────────────────┐
│                  唯一权威版本档案                       │
│          GitHub 私有仓库 <黄龄新浪博客>                  │
│   (git commit 记录每次变更 / 可回滚 / 可迁移 / 可 clone)  │
└──────────────────────┬───────────────────────────────┘
                       │ push                
        ┌──────────────┼──────────────┐
        │ 部署         │ 备份         │
        ▼              ▼              ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 主：国内托管  │  │ 备1：本地磁盘 │  │ 备2：GitHub  │
│ 阿里 ESA      │  │ (项目根)     │  │ (仓库本身即   │
│ Pages/腾讯    │  │ 离线随时可看  │  │ 内容备份)     │
│ EdgeOne Pages │  │              │  │              │
└──────┬───────┘  └──────────────┘  └──────────────┘
       │ 手机浏览器输入 URL 即可访问（国内快）
       ▼
  手机随时翻看 ✅
```

**每一环崩塌都不致命：**
- GitHub 被墙 / 慢 → 内容仍在本地 + 国内托管
- 国内托管出问题 → 从 Git 仓库重新部署到另一家
- 本地电脑坏 → GitHub 仓库兜底恢复

## 2. 平台选型（含决策理由，便于后续复核）

### 2.1 访问层（主）：国内静态托管 —— 阿里 ESA Pages 或 腾讯 EdgeOne Pages，二选一
| 维度 | 阿里云 ESA Pages | 腾讯 EdgeOne Pages |
|---|---|---|
| 国内访问 | ⚡ 阿里 3200+ 边缘节点，百毫秒 | ⚡ 腾讯国内节点，秒开 |
| 部署方式 | Git 一键 / 拖拽上传 / CLI | Git 一键 / 拖拽上传 / CLI |
| 免费额度 | 对本项目完全够用 | 对本项目完全够用 |
| HTTPS / WAF / 防爬 | ✅ 原生 | ✅ 原生 |
| 与 GitHub 联动 | 从 GitHub 仓库拉取，push 自动构建 | 同左 |

> **结论**：两款能力等价，任选其一。**二选一去哪家，取决于你可用的云账号 / 发开票 / 生态偏好。** 默认推荐**阿里 ESA Pages**（阿里云账户通常更普遍），若你已有腾讯云生态则 EdgeOne 亦可。本次不锁定，文档在 §5 给两套并行的操作路径。

### 2.2 内容层（备/源）：GitHub 私有仓库 —— 唯一的版本权威
| 能力 | 说明 |
|---|---|
| 版本管理 | `git commit` 记录每次增删改，`git revert` 可回滚 |
| 可迁移 | 仓库可整体 clone / push 到别处，不锁定平台 |
| 访问控制 | 私有仓库，仅你认为可见 |
| 长期可靠性 | 平台存活度高、社区驱动 |

> GitHub 解决的是"**内容不会丢、历史能找回、可迁移**"；不负责"国内随时能打开"。这正是分工的原因。

## 3. 部署边界：打包什么、不打包什么

### ✅ 必须部署（离线文档主体）
```
index.html
page/          (324 个文章页)

```
> 三者相对路径互相引用，必须整体打包/上传，缺一不可。

### ⚠️ 构建输入（可选部署，供后续重新构建）
```
articles/      (源文章，便于拉新内容后重跑 build_html.py)
lists/
build_html.py / crawl_articles.py / download_images.py / enum_all.py
_manifest.json  (build_html 唯一依赖)
```
> 若只在"当前版本能访问"，可不部署这部分；若希望"以后能在线重新构建"，建议一并放进仓库（Git 层必然包含，属最稳妥）。

### ❌ 不要部署 / 不要入库（临时与调试产物）
```
根目录所有 _*.py / _*.json / _*.html / _*.md（下划线前缀 = 一次性脚本/中间产物/探测结论）
_wb/  (仅剩 local_ids.txt，一次性调试残留)
_恢复探测结论_11img.md / P2_残留内容清单.md（工作文档，不入部署包）
```
> 上传**会污染站点根目录**、浪费流量、还可能被搜索引擎抓到无意义页面。打包前务必先清理。

## 4. 打包 / 上传清单（阿里 ESA 与腾讯 EdgeOne 通用逻辑）

> 具体按钮名称以平台控制台为准，两地实现 Equivalent。下面用"通用步骤"表述。

### 4.A zip 手动上传路径（最简单，适合一次性）
1. 清理根目录临时产物（见 §3 ❌ 清单）——或仅拷贝下述白名单到新临时目录再打包
2. 生成白名单目录的 zip：`index.html + page/ + images/`
3. 登录 ESA / EdgeOne 控制台 → 找到 **Pages / 静态托管**
4. 新建项目 → **拖拽上传 zip**（或选择本地目录上传）
5. 平台自动部署 → 得到公网 `https://<你的子域名>.pages.xxx.com`
6. 可选：开启**访问口令 / 私有**（不想被搜索引擎收录时）
7. 手机浏览器打开该 URL 验收（见 §6 验收清单）

### 4.B Git 联动路径（推荐，支持后续自动更新，核心）
1. 在 GitHub 建**私有仓库**（如 `huangling-blog-archive`）
2. 本地项目根执行 `git init`，用 §3 白名单 + `.gitignore`（忽略所有 `_*`）做首次 commit
3. push 到 GitHub
4. 在 ESA/EdgeOne 控制台新建 Pages 项目，**连接该 GitHub 仓库**
5. 平台配置项目根目录 = 仓库根，构建命令留空（因为已是纯静态成品，无需构建）
6. 部署完成 → 公网 URL
7. **后续更新**：本地改完 → `git push` → 平台自动触发重新部署（Continuous Deployment）

> 显式说明：本项目**无构建步骤**（`page/`+`images/` 已是成品），所以 Pages 平台"构建命令"留空、用静态目录直出即可，不要套框架构建。

## 5. 平台操作路径（更细的对照，任选一家执行）

### 5.A 阿里云 ESA Pages
1. 控制台 → 搜索「**ESA**」→「**Pages 静态站点**」
2. 新建项目：`Git 导入`（选 §4.B 的仓库）或 `上传文件`（选 §4.A 的 zip）
3. 若走 Git：选择分支（main）、构建命令**留空**、构建目录 `/`
4. 部署 → 得到 `https://<name>.esa.example.com`（由系统分配子域）
5. 访问控制：开启「登录鉴权 / 防爬」，可选

### 5.B 腾讯 EdgeOne Pages
1. 控制台 → 搜索「**EdgeOne**」→「**Pages**」
2. 新建项目：`从 GitHub 导入` 或 `上传`（逻辑同 5.A）
3. 构建设置：构建命令**留空**、输出目录 `/`（纯静态直出）
4. 部署 → `https://<name>.edgeone.app`
5. 访问控制：可加 Basic Auth / 访问口令

> **若两个平台都不愿意注册**，退路：GitHub Pages（`<user>.github.io`）也能发布，缺点仅是国内慢；或 Vercel/Netlify（国内访问不佳，不推荐为主）。

## 7. 更新 / 维护流程（日常增量）

### 场景 A：新增内容后重新构建并发布
```bash
# 1. 拉取新浪新文章 → 重新生成 page/ + images/ + index.html
python crawl_articles.py
python download_images.py
python build_html.py
# 2. 若走 Git 联动，commit + push 即自动触发重新部署
git add -A && git commit -m "新增内容: <说明>" && git push
# 3. 若走 zip 手动，重新打包白名单并到控制台重新上传
```

### 场景 B：改坏了想回退
```bash
git log              # 查历史
git revert <commit>  # 或 git checkout <commit> -- <文件>
git push             # 自动重新部署
```

### 场景 C：迁移到另一平台
```bash
# 仓库是自包含的，-clone 即可整体搬家到任何支持静态托管的平台
git clone <repo> 新目录
# 在新平台连接仓库 / 上传页面即可
```

### 场景 D：本地电脑故障
- GitHub 仓库是最新版本的兜底 → clone 到新机器即可恢复全部内容。

## 8. 风险与注意
- **内容在线风险**：部署成公网 URL 后，若不在平台开访问控制，可能被搜索引擎收录。黄龄博客本就公开，无隐私问题，但**建议开访问口令**以避免被无关爬取。
- **4 处 http 外链**：视频/活动图无法本地化，部署后在线可正常加载（平台访问公网），离线端显示占位，属已知预期。
- **`.gitignore`**：务必忽略 `_*`、`_wb/`、日志等，避免把临时产物打进仓库/部署包。
